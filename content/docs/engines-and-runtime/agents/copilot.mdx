Sentinel can also run a thread on GitHub Copilot, through the Copilot SDK.

The model runtime changes, but the thread model and app shell stay where they are.

## Setup

| What            | Details                                                                                  |
| --------------- | ---------------------------------------------------------------------------------------- |
| Runtime         | Bundled with Sentinel, so nothing needs installing                                       |
| Your own CLI    | Optional: `brew install copilot-cli` or `npm install -g @github/copilot`, then set it as the instance's binary path |
| Update          | The bundled runtime updates with Sentinel; your own CLI updates with `copilot update` or Homebrew |
| Recommended     | Copilot CLI 1.0 or newer, when you run your own                                          |
| Home variable   | `COPILOT_HOME`                                                                           |

Clearing the binary path goes back to the bundled runtime.

## Sign-in

- **Sign in with GitHub** runs `copilot login` in a terminal inside the Copilot card, into the instance's home.
- **Use a GitHub token** stores a fine-grained token with the Copilot Requests permission, encrypted on the instance as `COPILOT_GITHUB_TOKEN`.

## What Sentinel keeps for a Copilot thread

A Copilot-backed thread can carry:

- Copilot session ID
- working directory
- model
- reasoning effort
- the instance it runs on

That is enough for Sentinel to reopen the thread and keep the runtime connection lined up with the rest of the thread state.

The split is close to Claude Code.

Sentinel keeps the durable thread record. GitHub Copilot keeps the active local session.

## Runtime status and auth

Copilot has its own runtime-status surface inside Sentinel.

That status layer is doing a little more than simple model discovery.

The app checks whether the runtime is present, whether auth is ready, and whether the runtime can return the current model list in time.

That matters because a local runtime can be installed but still not be ready to run a thread if auth is missing.

## Model handling

Sentinel asks the local Copilot setup for runtime status and available models.

If the local runtime responds normally, the app uses those runtime models directly.

If the runtime is present and authenticated but model discovery times out, Sentinel can still surface a small fallback model list so the thread UI does not stall out.

That fallback matters for the same reason it matters on Codex and Claude: local runtime checks can be a little uneven.

So here too, the app is trying to keep the thread stable even when runtime discovery is slower than the main UI expects.

## Run shape

GitHub Copilot sits in roughly the same product position as Claude and Codex:

```mermaid
sequenceDiagram
  participant UI as "Sentinel UI"
  participant ST as "Sentinel thread"
  participant CP as "GitHub Copilot runtime"

  UI->>ST: Start run on a Copilot thread
  ST->>CP: Resolve linked Copilot session and send request
  CP-->>ST: Stream output and runtime state
  ST-->>UI: Stream messages, status, approvals, and snapshots
```

The main difference is the runtime state surface. The outer product shape stays the same.

The session record is still smaller than the Codex one, but the pattern is familiar:

1. Resolve the saved Copilot-linked thread state.
2. Send the current turn into the Copilot session.
3. Stream output and status back through the thread.
4. Persist the updated state in Sentinel around the runtime.

## Permission and plan mode

Copilot threads use Sentinel's *Default* and *Full* permission modes. In *Default*, shell, read, write, and web requests follow your approval settings, and requests for MCP servers, custom tools, hooks, and extensions always ask.

Copilot has no plan mode Sentinel can drive, so plan mode uses Sentinel's plan prompt.

## Code shape

The Copilot state surface is defined explicitly in the runtime types:

```ts
export const copilotThreadStateSchema = z.object({
  ...threadStateSessionMeta,
  cwd: z.string().nullish(),
  modelId: z.string().nullish(),
  reasoningEffort: z.enum(REASONING_EFFORTS).nullish(),
  sessionId: z.string(),
});
```

## What stays in Sentinel

Even when GitHub Copilot is running the thread, Sentinel still owns:

- the thread list
- the workspace state
- the repo panels
- the shell
- settings

So the runtime changes, but the rest of the product stays steady.
